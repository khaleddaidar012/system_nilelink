# نسخ D1 والملفات خارج الجهاز — تجربة staging

أُنشئ Worker مستقل `nilelink-d1-staging-backup` على حساب الوجهة، وجدول يومي `0 1 * * *` بتوقيت UTC. المصدر هو **نسخة النقل التدريبية السابقة** `nilelink-d1-staging` وملفاتها `nilelink-d1-staging-files`، وليس MongoDB الحالية أو قاعدة E2E أو الإنتاج. الوجهة bucket خاصة جديدة `nilelink-d1-staging-backups` دون رابط تنزيل عام.

## ما تم اختباره

نُشر Worker بالإصدار `6a6224ba-d54b-4dd8-8d4d-11b5f6adf384`، وأُضيف مفتاحا التشفير والتشغيل كأسرار. يتطلب POST `/run` مفتاح تشغيل عشوائيًا؛ الطلب بلا مفتاح أعاد 404. الجدول منشور، ولم يُرصد أول Cron Event بعد. استُخدم endpoint المحمي لاختبار نفس وظيفة النسخ على Cloudflare فعليًا.

في 20 أكتوبر 2026 أُنشئت النسخة `1091b6b0-9d35-43d0-b7f0-ba732b4f8d03`: 10,651,054 بايتًا مشفرًا. قرأ Worker الجداول الـ23 في batch واحدة، وفحص المخطط والسلامة والعلاقات، وقرأ الملفات الـ53 وطابق حجمها وSHA-256 بالقائمة المعتمدة، ثم أعاد قراءة قاعدة البيانات ورفض اختلافها. القيم تشمل نص JSON الأصلي وrevision والأعمدة الداخلية للعدادات وطابور الإرسال وجورنال الملفات. المخطط محفوظ لإعادة إنشائه؛ جداول Cloudflare الداخلية و`d1_migrations` خارج هذه الصيغة التطبيقية.

شُفرت الحزمة بواسطة AES-256-GCM مع IV عشوائي وربط التشفير بمفتاح الكائن. تحقق Worker من النسخة بعد تخزينها بالقراءة وفك التشفير قبل نشر علامة الاكتمال. لم يكتب في D1 أو bucket ملفات المصدر ولم يحذف نسخة سابقة.

نزّل `scripts/d1/validate-cloud-backup.mjs` الكائن المخزن من R2 عبر binding منفصلة، وفكّه، وأعاد إنشاء D1 كتجربة SQLite محلية جديدة مع العلاقات، وقارن كل الأعمدة والصفوف، ثم كتب الملفات إلى مجلد جديد بأسماء رقمية آمنة وقارن البصمات بعد قراءتها من القرص:

- 2072 سجلًا عبر 23 جدولًا؛ `quick_check=ok` وصفر مخالفات علاقات.
- 53 ملفًا، بمجموع 7,216,764 بايتًا؛ جميع البصمات مطابقة.
- استثناء واحد محفوظ: الملف التجريبي الذي لا توجد له بايتات أصلية. النسخة لا تدعي احتواءه.

التقرير والأدلة الخاصة: `.private/d1-migration/cloud-backup/staging-v1/validation/ef924556-3064-44cc-b7a3-86762c2019e9/report.json`، الحالة `cloud-backup-and-restore-verified`. ظهرت رسالة WSARecv عند إغلاق اتصال workerd المحلي بعد اكتمال التقرير؛ خرج الفحص برمز صفر.

## الإعداد والتشغيل

- المصادر: `scripts/d1/cloud-backup-core.mjs` و`cloud-backup-worker.mjs`، وتجهيز أولي بـ`prepare-cloud-backup.mjs`. ملفات الإعداد والقائمة والأسرار داخل `.private/d1-migration/cloud-backup/staging-v1/`، ولا تُنشر في Git أو المحادثة.
- النسخة لا تحمل قيمة productionCertified=true. تغيير المصدر إلى الإنتاج يحتاج قائمة ملفات وإعدادات معتمدة، ونسخة حديثة من البيانات، واختبارًا جديدًا.
- مفتاح فك التشفير محفوظ محليًا في ملف الأسرار الخاص وبداخل Worker Secrets؛ **يلزم الاحتفاظ بنسخة آمنة مستقلة منه** قبل اعتماد هذه الآلية للإنتاج. فقدانه يمنع فك النسخ. لا يوضع داخل bucket النسخ ولا يرسل بالشات.
- bucket النسخ خارج الجهاز لكنها **داخل حساب Cloudflare نفسه**؛ لا تحمي وحدها من فقد الحساب. لا توجد نسخة ثانية في حساب أو مزود مستقل بعد.
- يوجد حد اختباري 5000 سجل، و10MiB للملف، و32MiB لمجموع الملفات، و48MiB للحزمة. تجاوزها يفشل صراحة؛ يلزم تصميم تقسيم وتدفق قبل نمو الإنتاج فوق هذه الحدود.
- لا توجد سياسة حذف أو مدة احتفاظ تلقائية. لن تُحذف نسخ دون سياسة معتمدة، ويجب متابعة الحجم والتكلفة. الجدول الحالي ينسخ baseline ثابتة يوميًا؛ لا يُعد نسخًا يوميًا للموقع الحالي.
- لا توجد بعد لوحة لاستعادة D1 أو تنبيه خارجي عند فشل Cron أو سجل تاريخي مركزي؛ سجل النجاح في R2 ورسائل التشغيل في Worker. نجاح التشغيل اليدوي لا يثبت تشغيل Cron تلقائيًا أو مراقبته.
- الباقتان بحسب آخر صورة لدى المستخدم مقررتان للانتهاء 11 نوفمبر 2026؛ استمرارية الخطة والوصول إلى R2 يجب حسمهما قبل اعتماد الإنتاج.

تختبر `tests/d1/cloud-backup.test.mjs` التشفير والملفات والنصوص والحقول الإضافية وrevision، وتمنع اكتمال نسخة عند فساد المصدر أو readback أو تغير قاعدة البيانات، وترفض مفاتيح خاطئة ومراحل غير معتمدة وطلب تشغيل غير مصرح.

## تمييز التشغيل المجدول وفحص النسخ الموجودة

نُشر تحديث بالإصدار `62162c78-37af-4be6-9d1a-94293ed72d35` مع بقاء نفس الجدولة والأسرار والمصادر. النسخ الجديدة تسجل `trigger: scheduled` من scheduled handler، أو `manual` من مسار التشغيل اليدوي؛ القيمة موجودة في الحزمة المشفرة وعلامة الاكتمال، ولا يستقبلها endpoint من المستخدم. نجح اختبار handler المحلي، وصارت اختبارات هذه المجموعة 9/9. لم ننشئ نسخة يدوية أخرى لإيهام نجاح الجدولة.

الأمر `node --use-system-ca scripts/d1/validate-cloud-backup.mjs --inspect` يقرأ قائمة العلامات ويفحص وجود الكائن المقابل وحجمه وبصمته الوصفية دون تشغيل النسخ. فحص 20 أكتوبر الساعة 16:45 UTC وجد النسخة اليدوية الأصلية وحدها؛ أول موعد تلقائي ما زال في 21 أكتوبر 01:00 UTC. النسخة القديمة قبل إضافة حقل trigger مصنفة `legacy-unknown` في الجرد؛ هوية تشغيلها اليدوي مثبتة في تقرير التحقق الأصلي.

الأمر `node --use-system-ca scripts/d1/validate-cloud-backup.mjs --restore-existing <backup-id>` يسترجع نسخة مكتملة موجودة إلى معمل محلي جديد بالقراءة فقط من R2؛ لا ينشئ نسخة بديلة. يفحص بصمة الكائن والتشفير والصفوف والعلاقات وبايتات كل ملف، ويطابق trigger والعدادات مع الحزمة المشفرة. لا يُكتفى بوجود علامة الاكتمال كدليل على اختبار الاسترجاع الكامل.

## Daily scheduling and recovery

The production backup Worker uses `*/5 * * * *` as a lightweight retry trigger. The daily backup window still begins at 01:30 UTC. A conditional R2 claim under `scheduled-days/YYYY-MM-DD.json` prevents concurrent captures, skips completed days only after checking their stored object and receipt, and caps attempts at three per UTC day. An abandoned claim can be retried after fifteen minutes. No customer data or old backup objects are deleted.

A run record is persisted before capture starts. Monitoring treats a fresh `processing` record as in progress and flags one older than fifteen minutes as uncertain. This makes interrupted runs visible even if the runtime exits before a catch handler can run. A manual backup does not conceal a missed automatic run.
