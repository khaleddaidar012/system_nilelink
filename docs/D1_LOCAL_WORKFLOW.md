# معمل نقل MongoDB إلى D1

هذه الأدوات مرحلة تجهيز وتجربة. التطبيق الحالي يستخدم MongoDB افتراضيًا. أصبحت مسارات الحسابات والصلاحيات والعملاء والمستندات والطلبات والعروض والإشعارات والتصنيفات تدعم اختيار D1 للتجربة المحلية صراحةً. لا توجد آلية fallback صامت أو خلط كتابات بين المحركين، ولا نشر أو نقل بعيد ضمن هذه الأوامر.

## الملفات

- `migrations/d1/0001_document_tables.sql`: الجداول الـ19 وقيود الهوية والـunique والعلاقات والفهارس. كامل السجل محفوظ داخل JSON، مع generated columns مفهرسة للبحث والربط. تغيير المستند يحدّث الإسقاط تلقائيًا.
- `lib/db/d1.ts`: عقد binding واتصال D1 الخاص بطلب Cloudflare، دون الاحتفاظ به عالميًا. يحتاج binding فعليًا قبل استخدامه في التطبيق.
- `lib/db/repositories`: repositories للمستخدمين والحسابات والعملاء والأدوار وعدادات الفواتير. `lib/accounts/d1-handlers.ts` ينفذ مسارات الحسابات على D1، بينما يبقى مسار MongoDB الحالي هو الافتراضي.
- `lib/workflows`: تنفيذ الطلبات والخدمات والعروض والمستندات والإشعارات والتصنيفات، مع معاملات تحفظ التغييرات والسجلات والإشعارات معًا.
- `migrations/d1/0003_workflow_support.sql`: عدادات الطلبات والعروض، وسجل الملفات التي تنتظر تأكيد بياناتها، وفهرس ربط المستندات بالطلبات.
- `wrangler.d1.local.jsonc`: إعداد محلي منفصل بقاعدة placeholder. لا يُستخدم للنشر؛ UUID الصفري ليس قاعدة بعيدة.
- `scripts/d1/export-mongo.mjs`: تصدير قراءة فقط لكل collections، باستخدام MongoDB driver مباشرة وBSON خام. لا يحذف أو يعدل المصدر.
- `scripts/d1/rehearse.mjs`: فحص النسخة ونقلها إلى محاكي D1 مؤقت ثم مقارنة كل سجل. المحاكي غير دائم ويُغلق في النهاية حتى عند الفشل.

## التشغيل المحلي

يلزم Node.js 22.18 أو أحدث لدعم TypeScript مباشرة في الاختبارات؛ تم التحقق على Node.js 24.19.0. إصدار Miniflare مثبت مباشرة ضمن devDependencies وموجود أصلًا في شجرة الاعتماديات.

```powershell
npm run test:d1
npm run d1:migrate:local
```

لتجربة D1 في نسخة تطوير محلية فقط، بعد تطبيق migrations:

```powershell
$env:DATABASE_PROVIDER = "d1"
$env:D1_MIGRATION_PREVIEW = "true"
npm run dev
```

يختار OpenNext الإعداد `wrangler.d1.local.jsonc` في هذه الحالة. قاعدة المعمل فارغة بعد إنشاء المخطط؛ يمكن إنشاء حساب جديد من صفحة التسجيل. لا تنشئ صفحة الدخول حسابات manager/staff افتراضية على D1. اختبارات `npm run test:d1` تنشئ مديرًا وبيانات وهمية في قاعدة مؤقتة منفصلة، ولا تضيفها إلى قاعدة التطبيق المحلية.

المسارات التي لم تُحوّل بعد سترفض الوصول إلى MongoDB عند اختيار D1. تفعيل `DATABASE_PROVIDER=d1` في production ممنوع في الكود إلى أن يكتمل تحويل النظام. لا تستخدم وضع المعمل لخدمة المستخدمين الفعليين. العلم القديم `D1_ACCOUNTS_PREVIEW` يظل مدعومًا فقط عندما لا يوجد `D1_MIGRATION_PREVIEW`.

ملفات التجربة الجديدة تُكتب محليًا داخل `.private/d1-preview-files` المستبعد من Git. رفعها وتنظيفها لا يكتب أو يحذف من R2 الحالية. قراءة مفتاح مستورد غير موجود محليًا تستخدم بوابة التخزين الأصلية للقراءة فقط بعد فحص صلاحية المستخدم. الاختبارات تحقن تخزينًا وهميًا ولا تتصل بـR2 أو ترسل رسائل.

للعودة إلى اختيار MongoDB، أوقف خادم التطوير ثم أزل المتغيرين من جلسة PowerShell وأعد التشغيل:

```powershell
Remove-Item Env:DATABASE_PROVIDER
Remove-Item Env:D1_MIGRATION_PREVIEW
npm run dev
```

الأمر الثاني يطبق المخطط داخل `.wrangler/state/v3/d1`. لا يتصل بقاعدة Cloudflare البعيدة. إعادة تشغيله آمنة عبر سجل migrations.

## نسخة المصدر

راجع اسم قاعدة المصدر وملف البيئة الخاص بها قبل التشغيل. المثال التالي يقرأ URI من `.env.local` ويختار قاعدة `nilelink` صراحةً:

```powershell
node --env-file=.env.local scripts/d1/export-mongo.mjs --database nilelink
```

الأداة تصدر إلى `.private/d1-migration/<unique-id>`، وهو مسار مستبعد من Git. الملفات تحتوي بيانات شخصية وكلمات مرور مشفرة وtokens؛ تبقى محلية ولا تُرفق في المحادثة أو PR. لملفات Windows تعتمد صلاحيات الوصول الفعلية على ACL للمجلد، وليس قيمة mode وحدها.

تحتوي النسخة على BSON الأصلي لكل سجل، مع SHA-256 لكل سجل ولكل ملف، وأسماء collections وindexes وmetadata. لا تمر عبر Mongoose، ولذلك لا تفقد `passwordHash` أو الحقول غير المعروفة. فشل التصدير لا يكتب manifest مكتملًا صالحًا للاستيراد.

هذا تصدير وليس ضمانًا لنسخة في لحظة واحدة أثناء استمرار الكتابة. `majority` للقراءات ليس snapshot موحدًا عبر collections. يجب الاحتفاظ أيضًا بـmongodump مجرب الاستعادة. عند النقل النهائي فقط، وبعد منع كل الكتابات بالفعل وانتظار الجاري منها، يمكن إضافة `--writes-frozen` لتسجيل إقرار المشغل؛ الخيار لا يمنع الكتابة بنفسه ولا يشهد بصحة النقل.

## تجربة النقل والمطابقة

```powershell
node scripts/d1/rehearse.mjs .private/d1-migration/<unique-id>
```

تتحقق الأداة من checksums والأعداد والهوية وأنواع BSON، ثم تنشئ مخططًا جديدًا داخل محاكي D1 مؤقت. تُنقل البيانات على دفعات صغيرة وفق ترتيب العلاقات. علاقة العميل بالموظف المسؤول تُستعاد بعد وجود المستخدمين، ويُقارن المستند النهائي كاملًا بالأصل المحول. لا يتغير ملف المصدر.

توقف التجربة عند:

- collection غير محصورة، حتى لو كانت فارغة؛ يلزم mapping ومراجعة صريحة.
- اختلاف checksum أو عدد، أو تكرار ID أو كسر قيد unique أو علاقة مطلوبة.
- BSON يحتاج mapping خاصًا، مثل Long وDecimal128 وBinary وRegex، أو رقم غير محدود أو negative zero، أو هوية غير نص/ObjectId.
- تغير BSON عند deserialize/serialize، مثل duplicate keys التي قد يخفيها JavaScript.
- سجل يتجاوز الحد التحفظي الحالي البالغ 1,500,000 بايت بعد التحويل. هذا أقل من حد D1 للصف ويترك مساحة، لكنه لا يثبت تلقائيًا ملاءمة كل سجل وفهرس للحدود البعيدة.

لا تُحذف السجلات المرفوضة ولا تُقرب المبالغ لتجاوز أخطاء النقل. BSON الخام يظل محفوظًا لإضافة mapping مراجع ثم إعادة التجربة. تواريخ Date تتحول إلى ISO UTC بدقة milliseconds، وObjectId إلى النص الأصلي؛ BSON يبقى المرجع للحفاظ على نوع المصدر.

عند النجاح يُكتب تقرير جديد باسم `local-rehearsal-<unique-id>.json` داخل النسخة. يوضح أنه تحقق محلي فقط، ويترك `cutoverCertified: false`. المطابقة لكل سجل تشمل المبالغ المخزنة كما هي، لكنها ليست بديلًا لاختبار حسابات التطبيق أو مطابقة كشوف الحساب والملفات الفعلية.

## حدود هذه المرحلة وما يتبقى

تم ربط 22 ملف API routes بمسار D1 اختياري يشمل الدخول والتسجيل وتجديد الجلسة، التحقق وتغيير الاتصال وكلمة المرور، الملف الشخصي، الموظفين والأدوار، وقوائم العملاء وتفاصيلهم وحالاتهم. القراءة المرتبطة بالمستندات والإشعارات والطلبات وملخص الفواتير في هذه المسارات تأتي من D1 أيضًا.

التسجيل ينشئ العميل والمستخدم في batch واحدة مع منع تكرار رقم السجل أثناء السباق. تعديل المستخدم والشركة وتغيير حالة العميل مع إشعاراته معاملات ذرية. تحديثات الحسابات تستخدم revision وguard يفشل عمدًا عند تحديث صفر صفوف، لمنع اعتماد نصف عملية أو الكتابة فوق تعديل متزامن. يجب إعادة تحميل البيانات عند استجابة 409.

تُقرأ حالة المستخدم وصلاحياته وعلاقة عميله من D1 في كل طلب محمي. الجلسة القديمة لا تمنح دورًا تمت إزالته ولا تسمح بتعديل شركة مختلفة. الاستجابات تستخدم حقولًا محددة ولا تصدر passwordHash أو OTP أو tokens أو حقول المصدر الإضافية.

اختلافات مقصودة في وضع D1 المحلي، وتحتاج اعتماد اختبارها قبل الإنتاج:

- رفض دخول الحسابات inactive/suspended ورفض refresh token كجلسة access.
- عدم إنشاء بيانات تجربة من صفحة الدخول، وعدم إصلاح علاقات العملاء بكتابات خفية أثناء GET؛ العلاقة المفقودة تتطلب مراجعة نقل وتنتج 409.
- رموز التحقق المخزنة والعشوائية والمنتهية فقط مقبولة؛ لا يُقبل رمز WhatsApp المحسوب من رقم الهاتف، ولا رمز بلا تاريخ انتهاء. رموز reset/verification المستهلكة لا تُقبل عند إعادة الطلب.
- منع المشرف من تعطيل حسابه، وقراءة صلاحيات الموظف الحالية بدل الاعتماد على JWT قديم.
- حذف العميل نهائيًا متوقف في وضع D1 ويرجع 409، لحين تصميم سياسة تحفظ الروابط والسجلات المالية والتاريخية. لا يوجد حذف جزئي أو cascade صامت.
- البحث يحافظ على regex الحالي عبر ترشيح النتائج في التطبيق، لذلك يلزم قياسه على أحجام المصدر الفعلية قبل اعتماد الإنتاج. عناوين الأدوار تُقارن كنصوص حرفية باستخدام JavaScript lower-case، ويُشترط داخل المعاملة ألا تتغير مجموعة الأدوار منذ فحصها، بما يحمي اختلاف حالة الحروف في Unicode أيضًا. قد يتطلب إنشاء دورين بالتزامن إعادة أحد الطلبين بعد استجابة 409 حتى لو اختلف الاسمان.
- مسار forgot-password القديم يولد token فقط كما في النظام الحالي؛ توصيل رابط reset بالبريد وإزالة logging/preview للرموز من خدمات الإرسال القائمة مراجعة مطلوبة قبل الإنتاج. اختبارات D1 تحقن مرسلًا وهميًا ولا ترسل رسائل فعلية.

## مرحلة المستندات والطلبات والعروض

أضيف دعم D1 إلى 35 ملف routes أخرى، ليصبح المجموع 57 ملفًا مع مرحلة الحسابات. يشمل ذلك إنشاء الطلبات وخدماتها، الاستعلام والتسعير والتحديثات والامتثال، إنشاء العروض وتعديلها واتخاذ القرار، المستندات ورفعها وتنزيلها ومراجعتها، الإشعارات والتصنيفات وقواعد التسعير.

- إنشاء الطلب وخدماته وإشعاراته معاملة واحدة. الأرقام الجديدة تستخدم عدادًا ذريًا يبدأ بعد أعلى لاحقة رقمية تاريخية للسنة، دون تغيير الأرقام القديمة. حجز رقم لعملية فشلت قد يترك فجوة؛ الرقم لا يعاد استخدامه.
- العرض وخدماته يجب أن تخص نفس الطلب والعميل. قبول/رفض عرض متزامن لا ينتج قرارين؛ لا يُقبل عرض منتهي أو أقدم من أحدث عرض للطلب، ولا يُعاد تعديل عرض مقبول. تحديث بنود العرض يحتفظ بالـIDs والتاريخ؛ البنود المحذوفة من العرض تُؤرشف ولا تُمسح من القاعدة.
- الطلبات الجديدة تتطلب حساب عميل موثق البريد وفي حالة تسمح بالخدمة. الصلاحيات وعلاقة العميل تُقرأ من D1، وليس من claims قديمة.
- كل ملفات الدفعة تُفحص قبل بدء التخزين. بيانات الملفات وسجل الرفع والإشعارات وتحديث الطلب تحفظ معًا. زيادة revision العميل تمنع تجاوز الحصة أثناء الرفع المتزامن.
- `_nilelink_storage_pending` يسجل المفاتيح قبل التخزين ويحذفها عند تأكيد بيانات المستند. عند فشل مؤكد، يُنظف فقط ملف جديد لا تشير إليه أي بيانات مستند. عند انقطاع D1 أو عدم اليقين لا يُحذف الملف، ويظل مسجلًا للمصالحة. يتبقى مشغل مصالحة دورية لهذه السجلات قبل الإنتاج؛ لا يجوز حذفها أو ملفاتها بالجملة.
- لا يتم استبدال ملف قديم. تنزيل الملفات يتحقق من الحجم والـhash المتاح للبيانات المقروءة كاملةً، ويرفض الاختلاف للمراجعة. حذف مستند من واجهة D1 يؤرشفه ويحفظ بياناته وملفه وسجله؛ لا يزيله ماديًا.
- مراجعة مستند تحفظ الحالة وصحة حساب العميل والسجلات والإشعارات معًا. الحالة pending_review لا تنشئ إشعار رفض. لا يبدأ إعداد عرض للطلب إلا بعد قبول كل مستنداته المقدمة النشطة، ولا تعيد المراجعة طلبًا قيد التشغيل إلى مرحلة المستندات.
- قراءة الإشعار العام أو الموجه للشركة تُسجل لكل مستخدم، ولا تجعل الإشعار مقروءًا لبقية الموظفين/العملاء. لا يمكن تعليم إشعار موجه لمستخدم آخر كمقروء. العدادات تستخدم نفس قواعد الرؤية.
- التنبيه اليدوي يحفظ طلب إرسال بحالة pending ويرجع 202، ولا يدعي نجاح إرسال بريد أو واتساب. يتبقى عامل إرسال مع إعادة محاولة آمنة وتأكيد التسليم. هذا اختلاف صريح عن مسار MongoDB الذي يضع sent دون إرسال فعلي.
- حدود الدفعات الجديدة: 20 خدمة للطلب و20 بندًا للعرض و20 ملفًا للرفع الواحد، مع التزام حصة العميل وحجم 10MB للملف. يلزم قياس عدد الاستعلامات وزمن المعاملات وحجم الداتا على خطة Cloudflare الفعلية قبل الإنتاج.

لم نفحص MongoDB الحية ولم ننشئ قاعدة بعيدة. يتبقى استكمال الإرسال الفعلي والنسخ الاحتياطي البعيد، ومصالحة ملفات الرفع، واختبارات الواجهات والمطابقة المالية والملفات والاستعادة، وتجهيز الخطوط وPDF والتخزين للعمل على Workers، ثم اختبار staging بعيد قبل اعتماد نافذة النقل النهائي.

## تسجيل المدفوعات على D1 محليًا

أضيف مسار `POST /api/admin/payments` في هذه المرحلة، ثم أضيفت دورة المسودات والتأكيد الموضحة أدناه. تختبر المالية حاليًا على fixtures أو نسخة مستوردة في المعمل فقط.

- يلزم هيدر `Idempotency-Key` فريد لكل دفعة من 16 إلى 128 حرفًا من الحروف الإنجليزية والأرقام و`_` و`-`. عند إعادة إرسال نفس الدفعة بعد انقطاع الاتصال يستخدم المستدعي المفتاح نفسه ونفس المدخلات؛ لا يولد مفتاحًا جديدًا للمحاولة. الطلب الجديد يرجع 201، وإعادة الطلب الناجح ترجع 200 و`replayed: true`. إعادة استخدام المفتاح مع بيانات مختلفة ترجع 409. عميل API القديم الذي لا يرسل الهيدر يحتاج تحديثًا قبل استخدام D1.
- الدفع وتحديث الرصيد وسجل المراجعة معاملة واحدة، بصلاحية الموظف الحالية وفحص revision الفاتورة والعميل والمستخدم. أي تعارض متزامن يرجع 409 دون دفع جزئي؛ عنده تعاد قراءة الفاتورة قبل أي إجراء جديد.
- العميل والعملة يجب أن يطابقا الفاتورة، وتُرفض المسودات والملغاة والمدفوعة بالكامل والدفعات التي تتجاوز الرصيد. يدعم المسار EGP وUSD وEUR، بوحدات نقدية من منزلتين، دون تعديل بيانات المصدر أثناء الاستيراد.
- القيم القديمة لا يعاد تقريبها أو حسابها عند الاستيراد. قبل دفع جديد يفحص المسار اتساق الإجمالي والمدفوع والمتبقي ومجموع سجلات الدفعات وعلاقاتها وعملاتها. اختلاف أو دقة غير مدعومة يرجع 409 للمصالحة؛ لا يصحح البيانات تلقائيًا. هذه حماية تشغيلية وليست بديلًا للمطابقة المالية الشاملة قبل الإنتاج.
- migration `0004_payment_idempotency.sql` يضيف فهرس تفرد للمفاتيح الجديدة فقط؛ السجلات المستوردة دون مفتاح لا تتغير.

## مسودات الفواتير والتأكيد

أضيفت أربعة ملفات routes: قائمة/إنشاء الفواتير، تفاصيل/تعديل/أرشفة المسودة، التأكيد، ومعاينة الرقم التالي. أضيفت بعدها مسارات القراءة والإلغاء وPDF الموضحة أدناه؛ المجموع الحالي 69 ملف routes يدعم D1 محليًا.

- يحافظ الإنشاء والحساب على محرك `calculateInvoiceTotals` الحالي؛ لا يغيّر نسب الضرائب أو طريقة احتسابها. يلزم 1-100 بند، وقيم محدودة وآمنة، وتواريخ تقويم صحيحة، وموعد استحقاق لا يسبق الإصدار. لا يعاد حساب السجلات عند الاستيراد.
- عداد `INV_YYYY` يبدأ بعد الأكبر من العداد المستورد وأعلى لاحقة رقمية موجودة في `INV-YYYY-...`. الحجز ذري، ومعاينة الرقم لا تكتب شيئًا. سنة الترقيم هي سنة الإصدار بتوقيت UTC. فشل الحفظ بعد حجز رقم قد يترك فجوة؛ لا يعاد استعمال الرقم.
- لا يجوز جمع عميل مسجل وعميل خارجي في الإنشاء. الطلب والعرض إن وجدا يجب أن يتبعا نفس العميل، والعرض نفس الطلب والعملة. يعاد فحص العلاقات والصلاحيات الحالية داخل معاملة الحفظ باستخدام revision.
- الإنشاء والتعديل والتأكيد والأرشفة تحفظ سجل المراجعة مع الفاتورة ذريًا. التعديل يحفظ بيانات ما قبل التغيير كاملةً في السجل، ويحافظ على الحقول الإضافية للفاتورة والبنود التي يجري تعديلها. لا يسمح تعديل/تأكيد/أرشفة مسودة تحتوي على دفعات دون مصالحتها أولًا.
- التأكيد يحتاج `editInvoice`، وكل تعديل أو تأكيد لفاتورة ضريبية يحتاج `issueTaxInvoice` حتى لو لم يرسل المستدعي تغيير نوعها. بعد التأكيد تتوقف كتابة المسودة؛ التأكيد المتزامن لا يكرر السجل أو إشعار العميل.
- قبل التأكيد تقارن مبالغ المسودة والبنود بالمحرك الحالي، ويُرفض الاختلاف للمراجعة دون إعادة كتابة المصدر. الحالة بعد التأكيد تراعي قيمة صفرية (paid) أو تاريخ استحقاق قديم (overdue) كما في model الحالي.
- تفاصيل المصدر تبقى قابلة للقراءة حتى لو كانت المبالغ القديمة تحتاج مراجعة. ملخص كل عملة مستقل؛ الدقة غير المدعومة أو تجاوز حدود الجمع يجعل ملخص تلك العملة `null` مع `reconciliationRequired` بدل تقريبها أو إخفاء السجلات. الواجهة تعرض العملات منفصلة وحالة المراجعة.
- DELETE للمسودة يؤرشفها مع `status=cancelled` ويحفظ رقمها وtoken والبنود والسجلات؛ لا يحذفها ماديًا. الأرشيف مستبعد من القائمة العادية ويمكن للموظف قراءته عبر التفاصيل.
- نسخة العميل والشحنة تُحفظ وقت التأكيد. قيم جهة الإصدار الافتراضية من مسار Mongo الحالي محفوظة كما هي، بما فيها الحقول الضريبية والبنكية الحالية؛ يلزم التحقق منها وربطها بإعدادات موثوقة قبل الإنتاج. لا يرسل التأكيد بريدًا أو WhatsApp؛ ينشئ إشعارًا داخل النظام فقط.
- البحث والتلخيص يقرآن المطابقات في التطبيق في هذا المعمل؛ يلزم تحسين/قياس الاستعلامات والذاكرة على حجم المصدر الفعلي قبل الإنتاج، مع اختبارات واجهة وتكامل staging.

## الإلغاء وقراءة العميل وكشوف الحساب وPDF

أضيفت سبعة ملفات routes: إلغاء الفاتورة، مالية العميل، قراءة الفاتورة عبر token، كشف الحساب الإداري وPDF له، وPDF الفاتورة للإدارة والعميل.

- إلغاء فاتورة صادرة غير مدفوعة يحتاج `editInvoice` والصلاحية الضريبية عند انطباقها. تحفظ الحالة والسبب والموظف والتاريخ وسجل ما قبل الإلغاء في معاملة واحدة. الفواتير ذات الدفعات أو الأرصدة غير المتسقة ترفض الإلغاء بـ409 لحين تصميم التسويات/عكس الدفعات، ولا تحذف أو تتجاهل المدفوعات. سباق الإلغاء مع الدفع له فائز واحد باستخدام revision.
- واجهة العميل تقرأ علاقة العميل الحالية من D1 وتستبعد المسودات والأرشيف. رابط token يبقى رابط مشاركة حاملًا للصلاحية كما في النظام الحالي، ويستبعد المسودات والأرشيف. المبالغ والسجلات الأصلية لا تعدل أثناء القراءة. بيانات العميل العامة تمر بقائمة حقول محددة، بما في ذلك البنود وsnapshots، فلا تخرج الملاحظات الداخلية وبيانات الموظف أو حقول الاستيراد غير المعروفة. قراءة الفاتورة والدفعات عبر token تستخدم SQL batch واحدة. تستعمل الاستجابات المالية `Cache-Control: no-store`.
- إجماليات العميل تفصل العملات وتظهر حالة المراجعة للدقة غير المدعومة بدل تقريب الأصل. الواجهة تعرض مجموع كل عملة مستقلًا.
- كشف الحساب يحتاج `viewCustomerStatements`، وPDF الكشف يحتاج `exportCustomerStatements`، من صلاحيات المستخدم الحالية. يدعم EGP وUSD وEUR كلًا منفصلة، وحدود تاريخ بصيغة YYYY-MM-DD وبأيام UTC ثابتة. هذه الحدود مقصودة لتطابق المحاكي وWorkers، بدل الاعتماد على توقيت جهاز التنفيذ.
- قراءة العميل وفواتيره ودفعاته من SQL batch واحدة لتجنب كشف يجمع فاتورة قبل الدفع مع دفعات بعده. رصيد الافتتاح من كل الحركات قبل بداية الفترة؛ الديون والائتمانات ورصيد النهاية من الفترة المحددة. التصفية حسب نوع الحركة تغير الصفوف المعروضة فقط ولا تغير الأرصدة. الترتيب ثابت: الوقت، ثم الفواتير قبل المدفوعات عند تساوي الوقت، ثم ID.
- يجمع الكشف بوحدات نقدية صحيحة مع فحص الأمان، ويرفض الدقة غير المدعومة أو الروابط المخالفة بين عميل/فاتورة/دفعة أو سجل دفعة على فاتورة ملغاة أو مسودة. لا يصحح الأرصدة أو يحذف الحركات تلقائيًا. تبقى قراءة الفاتورة الأصلية متاحة للمراجعة.
- PDF يعيد استخدام القوالب الحالية والخطوط المحلية. فحص الملكية والحالة والصلاحية يحصل قبل استدعاء مولد الملف. لا يسمح override النوع بتجاوز صلاحية فاتورة ضريبية. للعميل يسمح بتنزيل فاتورته الصادرة فقط. لا تغيّر عملية التنزيل البيانات ولا ترسل بريدًا.
- عند غياب customerSnapshot القديمة، تستخدم القراءة والعرض حقول العميل المرتبط بالفاتورة فقط؛ لا تعيد كتابة snapshot المصدر. كشف الحساب يستخدم tracking snapshot أو الطلب المرتبط بنفس العميل. لا تُستبدل snapshots المحفوظة ببيانات حية.
- اختبارات التكامل تنتج ملفين اصطناعيين داخل `.private/d1-migration/pdf-fixtures/` للفحص المحلي، وليسا بيانات مصدر. تمت معاينة ملفات PDF المحلية بصريًا. صُحح عرض ضريبة صفرية كانت تظهر 14% بسبب `|| 14` إلى `?? 14` دون تعديل الحساب أو البيانات.
- مسارا إرسال الفاتورة وكشف الحساب أصبحا يضيفان طلبًا إلى طابور المعمل الموضح أدناه دون إرسال فعلي. لم يرسل أي بريد أو WhatsApp. القوالب الحالية وقراءة الخطوط عبر fs ما زالت تحتاج تحققًا وتجهيزًا خاصًا بـWorkers قبل الإنتاج؛ نجاح PDF المحلي لا يثبت جاهزية النشر.

## طابور الإرسال وفحص الانتهاء وعزل النسخ الاحتياطي

أضيفت ثلاثة ملفات routes لمسار D1: إرسال الفاتورة، إرسال الكشف، وفحص انتهاء المستندات؛ المجموع الحالي 72 ملف routes. تطبيق migration `0005_delivery_jobs.sql` محلي فقط. لا يزال D1 محظورًا في production.

- مسارا الإرسال يحتاجان `sendFinancialDocuments` من صلاحيات الموظف الحالية، والصلاحية الضريبية للفاتورة الضريبية. يلزم `Idempotency-Key` لكل طلب، وتعيد المحاولة بنفس المدخلات والمفتاح نفس job. استخدامه لعملية أو مدخلات أخرى يرجع 409. واجهتا الإرسال تحتفظان بالمفتاح عند فشل الشبكة وتميزان queued عن sent.
- يحتفظ `_nilelink_delivery_jobs` بنسخة مجمدة من الفاتورة أو الكشف والجهة المستلمة، وبحالة pending و`previewOnly=true`. لا تُخزن الملاحظات الداخلية للفواتير داخل payload العميل. فاتورة الإرسال يجب أن تكون صادرة وغير ملغاة أو مؤرشفة؛ عنوانها من snapshot أو العميل المرتبط عند غياب snapshot. لا تقبل تغيير العنوان من body. الكشف يدعم عنوانًا مخصصًا صحيحًا وفترة وعملة محددتين.
- الفاتورة وsentAt وsentBy لا تتغير بمجرد وضع الطلب في الطابور. إنشاء job وسجل send_queued يتمان ذريًا مع مراجعة revisions للفاتورة والعميل والمستخدم. سقف snapshot في المعمل مليون بايت. أضيف عامل معالجة بمعاينة محلية كما هو موضح أدناه؛ لا توجد جدولة أو مزود إرسال فعلي موصول. يلزم توصيل مزود موثوق وسياسة مصالحة تشغيلية قبل الإنتاج، خصوصًا أن SMTP لا يضمن exactly-once.
- أصلح تمرير attachments في `sendEmail` إلى مزود البريد؛ كان المسار يحذف المرفقات رغم تجهيزها في routes. الاختبار يستبدل المزود بوهمي ويتأكد أن Buffer الملف يصل إليه؛ لا يرسل بريدًا. هذا التصحيح يفيد مسار Mongo أيضًا دون تعديل قاعدة البيانات.
- فحص انتهاء D1 يحتاج CRON_SECRET مضبوطًا صراحةً أو جلسة موظف حالي لديه canSendAlerts. لا يقبل السر الافتراضي الثابت الموجود في المسار القديم. لا توجد Cron Trigger جديدة أو جدولة أضيفت؛ المحول يدعم endpoint الحالي فقط.
- كل عميل يعالج في معاملة مستقلة تحفظ تحديث المستندات وحالة الحساب والسجلات وتنبيهات الشركة داخل التطبيق. revisions لكل المستندات والعميل تمنع فقد التحديث أو تكرار التنبيه عند تشغيلين متزامنين أو مراجعة/رفع متزامن. يعيد الرد عدد conflicts والحالات التي requiresReview، ويحتسب النتائج الناجحة فقط.
- تبقى حدود التذكير 30/20/10/5 يومًا مع فترات إعادة التنبيه الحالية، ويستعمل تاريخ الانتهاء الفعلي، بما في ذلك لحظة الانتهاء نفسها. lastNotificationQueuedAt يصف الإضافة إلى التنبيهات؛ لا يكتب lastNotificationSentAt ولا يدعي إرسالًا خارجيًا. تنبيهات هذا المعمل in_app فقط. تواريخ المصدر غير الصالحة تترك للمراجعة، ولا يعيد cron تنشيط حساب inactive قد يكون عليه حظر يدوي.
- جميع routes الخاصة بوكيل النسخ الحالي تمر عبر requireBackupAdmin. عند D1 يتحقق من الهوية والصلاحية الحالية ثم يرجع 503 و`D1_BACKUP_UNAVAILABLE`؛ لا يستدعي وكيل Mongo ولا يعرض نسخه كنسخ D1. يشمل الحاجز القائمة/الإنشاء/الحذف/الحماية/الاستعادة/الحالة. هذا عزل مقصود، وليس تنفيذًا لنسخ D1 الاحتياطي.
- أضيف نسخ محلي وتجربة استعادة معزولة تشمل الجداول الداخلية كما هو موضح أدناه. يتبقى النسخ والاستعادة للإنتاج، ونسخة أمان وخطة إيقاف الكتابة والمصالحة قبل أي استعادة فعلية. لا يكفي نسخ الجداول الـ19 الأصلية وحدها بعد بدء الكتابة على D1.

## نسخة D1 محلية وتجربة استعادة معزولة

```powershell
npm run d1:backup:local
npm run d1:restore:rehearse -- .private/d1-migration/d1-backups/<backup-id>
```

- يفتح الأمر قاعدة المعمل المحلية ذات UUID الصفري داخل `.wrangler/state/v3/d1` فقط؛ لا يقرأ أسرار Cloudflare أو عنوان قاعدة بعيدة، ولا يشغل وكيل Mongo. لا يغير سجلات التطبيق أثناء النسخ. النسخة الحالية الموجودة في قاعدة المعمل فارغة؛ اختبارات الاستعادة تستخدم fixtures ممتلئة منفصلة.
- النسخة المنطقية تجمع المخطط وجميع الصفوف ونتائج فحص السلامة في batch قراءة واحدة. تشمل الجداول الـ23: جداول التطبيق الـ19 وأربعة جداول داخلية، بما فيها طابور الإرسال والعدادات وسجل الملفات المعلقة. تحتفظ بنص data كما هو وبكل revision والقيم النصية، دون إعادة حساب مبالغ أو تغيير ترتيب JSON داخله.
- canonical schema وأسماء الجداول والأعمدة العادية تقارن مع migrations الحالية. أي جدول أو عمود أو index غير متوقع يوقف النسخ للمراجعة بدل إسقاطه. تُستبعد فقط بنية المحاكي `_cf_KV` و`_cf_METADATA` وجدول Wrangler `d1_migrations`؛ يحفظ hash migrations لتحديد الإصدار اللازم لإعادة الإنشاء.
- يكتب `backup.json.gz` ثم `manifest.json` أخيرًا داخل مجلد UUID جديد خاص وغير متتبع في Git. checksums للملف المضغوط والمحتوى ولكل جدول، مع الأعداد وأحجام الملفات وإصدار المخطط. لا تكتب فوق نسخة سابقة. SHA-256 يكشف التلف، وليس توقيعًا يثبت هوية مصدر الملف؛ النسخ محلية غير مشفرة وتحتاج حماية وتشفيرًا ونقلًا خارجيًا قبل الإنتاج.
- المعمل محدود بـ5000 سجل إجمالي و64 MiB غير مضغوطة، ولا يصلح هذا الحد كخطة لقاعدة الإنتاج قبل قياس حجم المصدر. الملفات الكبيرة أو revision/عداد SQL غير آمن يتوقف بدل تقريبه. محتوى JSON النقدي يبقى نصه الأصلي.
- تجربة الاستعادة لا تقبل binding هدف ولا تنفذ SQL من ملف النسخة. تنشئ محاكي D1 جديدًا غير مستمر، وتستخدم migrations المعروفة وINSERT بمعاملات مربوطة، وتؤجل فحص FK داخل معاملة لاستيعاب العلاقات الدائرية. تفحص counts وchecksums والروابط وquick_check وتقارن كل صف وrevision وقيمة حرفيًا، ثم تغلق المحاكي. لا توجد استعادة فوق القاعدة الحالية.
- الملفات الفعلية وR2 خارج النسخة، ويظهر ذلك صراحةً في manifest/report. يتبقى التحقق والنسخ الخاص بالملفات، ونسخ D1 البعيدة واستعادة staging وإدارة مفاتيح التشفير والاحتفاظ. لذلك لوحة النسخ الحالية تظل ترد `D1_BACKUP_UNAVAILABLE` ولا تُوصل بالوكيل القديم.

## عامل معالجة الإرسال: معاينة محلية وسياسة الحالات غير المؤكدة

```powershell
npm run d1:delivery:preview -- <delivery-job-id>
```

- الأمر يشغل عامل job واحدة على قاعدة المعمل فقط، ويستخدم sink محليًا يكتب ملف JSON يحتوي البريد وPDF بصيغة base64 داخل `.private/d1-migration/delivery-previews/`. لا يوجد فيه خيار live أو مزود شبكة. الملفات خاصة وقد تحتوي بيانات العميل ورابط الفاتورة؛ لا تنشرها.
- الافتراضي يحول pending إلى processing ثم previewed، ويحفظ hash مرفق PDF وسجلًا واضحًا بأنه لم يرسل بريدًا. لا يكتب sentAt أو sentBy أو status=sent للفواتير في المعاينة. يحد حجم المرفق بخمسة ملايين بايت، ويُهَرّب النصوص المدخلة في HTML.
- قبل حجز job يفحص المستخدم وصلاحية sendFinancialDocuments الحالية، وصلاحية الضريبة عند انطباقها، وحالة الفاتورة ومطابقة snapshot مع المصدر الحالي. تغيير الفاتورة منذ إدراجها يوقفها للمراجعة وطلب جديد، ولا يستبدل محتواها صامتًا. الكشف يستخدم نسخته المؤرخة والمجمدة.
- حجز job وتحديث revision الفاتورة عملية ذرية. عاملان متزامنان لا يستدعيان transport مرتين. الفاتورة التي لها job processing أو uncertain لا تلغى قبل المصالحة. عند توصيل مزود مستقبلًا سيحفظ receipt وسجل المراجعة وsent metadata معًا مع الحفاظ على تحديثات دفعات متزامنة.
- فشل PDF قبل استدعاء transport يسجل render_failed؛ انقطاع الرد بعد بدء transport أو فشل حفظ إيصال القبول يسجل uncertain، أو يترك processing إذا تعذر الوصول للقاعدة. لا توجد مهلة تعيد حجز هذه الحالات ولا إعادة إرسال تلقائية. يلزم فحص إيصال المزود وحالة الرسالة ثم قرار مشرف؛ استعادة نسخة قديمة لا تبرر إعادة إرسال jobs دون المصالحة.
- دالة العامل تقبل transport محقونًا لاختبارات قبول/انقطاع مزود وهمي. ترفض transport live لأي job لديها previewOnly إلا إذا كانت القيمة false صراحةً، ولا ينشئ مسار المعمل jobs من هذا النوع. لا يوجد adapter فعلي أو scheduler live حتى الآن، ولا ادعاء exactly-once عند المزود. sent تعني قبول المزود، ولا تثبت وصول الرسالة إلى صندوق المستلم.

المخطط أولي قابل للتعديل قبل الإنتاج بعد فحص المصدر، خصوصًا orphan references وindexes الفعلية. audit logs تحتفظ بعلاقاتها التاريخية كنصوص دون cascade أو اشتراط بقاء الكيان المحذوف. قيود unique تطابق التعريفات في الكود؛ إذا كانت indexes لم تُنشأ فعليًا على MongoDB فظهور تكرارات قديمة سيوقف التجربة للمراجعة.

في D1 يُستخدم `PRAGMA quick_check` و`foreign_key_check`، وتُختبر ذرية دفعات `batch()` عبر محاكي Workers. المراجع الرسمية:

## التحليلات وملخص الإدارة على D1

أضيفت أربعة ملفات routes: تتبع الزيارات، لوحة تحليلات الموقع، ملخص الحسابات والمستندات، وملخص النظام. المجموع الآن 76 ملف routes يدعم D1 محليًا. مسار seed القديم مرفوض صراحةً في D1 لمنع إنشاء حسابات تجريبية بكلمات مرور معروفة.

- التتبع يتحقق من نوع الحدث والمسار، ويشتق بصمة IP والجهاز والدولة من الطلب، ويتجاهل هوية الزائر المدخلة في body. يخفي query/hash ورموز مشاركة الفواتير ومعرفات الكيانات قبل حفظ الأحداث الجديدة. البيانات القديمة لا تعاد كتابتها.
- منع التكرار في نافذة 30 ثانية يتم داخل INSERT SQL واحدة وبساعة القاعدة، بما يشمل الطلبات المتزامنة. تعطيل التتبع لا يكتب بيانات.
- التجميع يستخدم SQL batch واحدة لعدادات الزوار والصفحات والأجهزة والدول وسبعة أيام UTC. التواريخ غير الصالحة أو المستقبلية لا تدخل أعداد الزيارات. تظهر مؤشرات مراجعة للبيانات القديمة غير الصالحة. لا تخرج الأحداث الخام أو بصمات الزوار في استجابة اللوحة، وتستخدم الاستجابات no-store.
- صلاحية اللوحة من مستخدم موظف حالي في D1، أو جلسة تحليلات بمفتاح مضبوط صراحةً؛ لا يقبل مفتاح fallback ثابتًا. ملخص الحسابات يحسب الإشعارات sent/delivered فقط، وليس مجرد اختيار قناة بريد.
- ملخص النظام لا يستدعي وكيل نسخ MongoDB ولا يفحص بريدًا خارجيًا. يعرض حالات غير متصلة/غير مؤكدة للنسخ والبريد، مع بيانات موظفين وسجلات مراجعة محددة الحقول فقط.
- نجح 142 اختبار D1، تشمل تسعة اختبارات جديدة للتحليلات والعزل والتزامن وتعطيل seed. نجحت أيضًا عشرة اختبارات قائمة لملخص الإدارة القديم بعد نقل hook الاختبار خارج ملف route ليتوافق مع Next.js.

## تخزين R2 التجريبي وPDF داخل Workers

أضيف `D1_STORAGE_MODE=r2-preview` كخيار صريح بدل قرص المعمل. الوضع الافتراضي يظل `local` لتظل الملفات التجريبية الموجودة قابلة للقراءة. لا تغير الوضع على قاعدة معمل تحتوي ملفات محلية قبل نسخها والتحقق منها؛ اختيار R2 لا ينسخها تلقائيًا.

- binding الكتابة `D1_PREVIEW_FILES` يجب أن يكون bucket تجريبيًا مستقلًا. binding المصدر `D1_SOURCE_FILES` اختياري وتستخدمه طبقة D1 للقراءة فقط. إعداد المعمل يعرّف bucketين محليين مع `remote: false`؛ لا يتصل بأي bucket حقيقية.
- الملفات الجديدة تحفظ تحت `_nilelink_d1_preview/` دون تغيير storageKey في سجل المستند. الرفع مشروط ذريًا بعدم وجود المفتاح، فلا يستبدل سباق رفع ملفًا محفوظًا. تحفظ بصمة SHA256 وتراجع عند القراءة مع الحجم؛ تلف نسخة المعمل أو فشل R2 لا يؤدي لقراءة بديل من المصدر.
- لا تستخدم بوابة R2 هذه مفاتيح S3 أو fallback إلى قرص محلي. غياب binding أو خطأ اسم الوضع يوقف العملية. الحذف ينحصر في namespace التجريبي؛ لا تستدعي الطبقة put/delete على binding المصدر. عند ربط buckets بعيدة لاحقًا يجب التحقق من استقلال وجهة المعمل فعليًا، حتى لو كانت أسماء bindings مختلفة.
- اختبارات محاكي Workers تشمل رفعًا متزامنًا، وبقاء الملف بعد إغلاق المحاكي وإعادة فتحه، ومطابقة البصمة ونوع الملف، وبقاء بايتات المصدر بعد الرفع والتنظيف، ورفض النسخة التالفة والمسارات غير الآمنة والـbindings المفقودة. هذه اختبارات R2 محلية وليست اختبار حساب Cloudflare الفعلي.

أضيف `PDF_ASSET_MODE=binding` لتحميل خطوط Amiri والشعار من `ASSETS` بمسارات ثابتة، ثم تمرير البايتات إلى PDFKit. لا يعتمد هذا الوضع على public/ على قرص Worker أو خطوط Helvetica الافتراضية. غياب الخطوط أو استجابة HTML بدلها أو حجم غير صالح يوقف التوليد، بدل إصدار ملف عربي ناقص. وضع Node المحلي يحتفظ بخط Amiri ثم Arial عند غيابه؛ غياب الاثنين يوقف التوليد أيضًا.

```powershell

```

الأمر يبني entry اختبار معزولًا يشغل مولدي الفاتورة وكشف الحساب الفعليين داخل workerd المحلي، ويمرر assets من binding محلي مع منع الشبكة الخارجية. ينتج ملفين اصطناعيين وتقريرًا داخل `.private/d1-migration/pdf-worker-fixtures/`. نجح الملفان وتمت معاينتهما بصريًا بعد التصيير إلى PNG. يختبر الأمر المولدات وقراءة assets، ولا يختبر تطبيق Next كاملًا أو صلاحيات API داخل Worker؛ تلك الصلاحيات تختبرها مجموعة اختبارات D1، ويلزم جمع المسارين في staging بعيد قبل الإنتاج.

## حساب Cloudflare مختلف وحصر الملفات قبل النقل

الوجهة المطلوبة حساب Cloudflare آخر، ويُحدد وقت تسجيل الدخول. لا تستنتج الحساب من Wrangler القديم أو متغيرات البيئة، ولا تستخدم إعداد الإنتاج الحالي لإنشاء D1. فحص whoami للقراءة فقط وجد جلسة منتهية؛ لم ينشئ موارد أو ينشر التطبيق.

```powershell
npm run d1:files:inventory -- <snapshot-directory>
npm run d1:files:inventory -- <snapshot-directory> --local-root <source-files-directory>
```

الأداة تتحقق أولًا من checksums نسخة BSON، وتحصر مفاتيح مستندات المصدر بما فيها المؤرشفة وتجمع المراجع لنفس الملف. لا تطبع URLs أو معرفات العملاء أو hashes في الطرفية؛ التقرير الخاص داخل مجلد snapshot. تحصر أيضًا fileUrl ومرفقات الطلبات وpdfUrl وavatarUrl والحقول المشابهة المحددة للمراجعة، دون تغيير الروابط التاريخية أو جلبها تلقائيًا. هذا الحصر لا يثبت تغطية أي بنية ملفات غير معروفة في حقول أخرى.

اختيار local-root يقرأ الملفات منه فقط، ويحسب SHA256 والحجم لكل مفتاح متميز، ويرفض الخروج عن المسار. غياب الملف أو تضارب metadata أو اختلاف البايتات يسجل مشكلة تمنع اعتماد النقل. غياب hash تاريخي يظهر صراحةً، ولا يدعي التقرير تحققًا لم يحدث. لا يكتب فوق الملفات ولا ينسخها ولا يغير MongoDB أو R2. يلزم بعد ذلك نسخ الملفات إلى حساب الوجهة ومقارنة كل ملف به وحفظ خطة نسخ/استعادة مستقلة. روابط الحساب القديم تحتاج mapping واضحًا قبل تحويل المستخدمين، ولا تُستبدل صامتًا في المصدر.

بعد تحديد Account ID الجديد وإنشاء قاعدة staging فيه:

```powershell
npm run d1:staging:prepare -- --account-id <destination-account-id> --database-id <staging-database-id> --database-name nilelink-d1-staging
```

الأمر يكتب إعداد D1 فقط داخل `.private/d1-migration/targets/<unique-id>/` ويثبت Account ID وDatabase ID وبصمة الإعداد والمخطط. يرفض القيم الوهمية واسم قاعدة لا يحدد staging. لا يحمل أسرار المشروع ولا يتضمن main أو R2 أو vars ولا ينشئ موارد أو ينفذ SQL أو deploy. يتضمن empty.env للاستخدام الصريح لاحقًا بدل ملفات dotenv الأصلية. دالة verifyStagingTarget ترفض اختلاف الحساب المتوقع أو تعديل الإعداد أو المخطط؛ هذا تحقق محلي، ولا يثبت ملكية القاعدة أو فراغها حتى يتم فحص الحساب الجديد عن بعد.

نجحت خمسة اختبارات إضافية لحصر الملفات وفحص البايتات وأخطاء المصدر وعزل حساب staging. لم يتم اختيار حساب الوجهة أو تسجيل الدخول إليه في هذه المرحلة.

تم فتح OAuth لتسجيل الدخول بالحساب الآخر بصلاحيات account:read وuser:read وd1:write فقط؛ لم تشمل الجلسة طلب نشر Workers أو تعديل R2. اكتمال التفويض واختيار Account ID وجهةً صراحةً مطلوبان قبل إنشاء staging. لا ترسل كلمات السر أو API Tokens في المحادثة. نجحت إعادة اختبارات المصدر وما قبل النقل: 14 اختبارًا تشمل تجربة الجداول الـ19 ومطابقة السجلات، وجميع الفحوص ببيانات اصطناعية فقط.

## إنشاء staging البعيدة على الحساب الجديد

تم التأكد من فراغ القاعدة الجديدة قبل تطبيق migrations الخمسة، ثم تطبيقها بنجاح عن بعد. فحص ما بعد التطبيق طابق DDL لجميع الجداول والفهارس مع migrations المحلية: 23 جدولًا و65 كائن مخطط إجمالًا. كل الجداول التطبيقية فارغة، وquick_check أعاد ok وforeign_key_check بلا مخالفات. التقرير `remote-schema-report.json` يحفظ هذه النتائج صراحةً ضمن نطاق المخطط فقط؛ لم تُقرأ MongoDB الحية ولم تُستورد بيانات عملاء ولم ينشر Worker.

الخطوة التالية: نسخة مصدر بصلاحية قراءة فقط، وتجربة نقل ومطابقة السجلات والمالية والملفات، واختبار استعادة D1 بعيدة. تفعيل D1 للإنتاج يظل محظورًا، واتصال الموقع الحالي لم يتغير. حساب OAuth الحالي منح صلاحيات الحساب وD1 فقط؛ تشغيل Workers وR2 يحتاج تفويضه المناسب عند الوصول لمرحلته، دون توسيع الصلاحيات قبل الحاجة.
