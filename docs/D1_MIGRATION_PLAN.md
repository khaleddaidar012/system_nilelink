# نقل Nile Link من MongoDB إلى Cloudflare D1

تاريخ المراجعة: 2026-10-17. الحالة: تم تنفيذ المخطط وأدوات التصدير والتجربة المحلية، وربط الحسابات والعملاء والمستندات والطلبات والعروض والإشعارات والتصنيفات بوضع D1 محلي اختياري. لم تُنقل بيانات حية وما زال MongoDB هو الاختيار الافتراضي. خطوات التشغيل وحدود المرحلة في `docs/D1_LOCAL_WORKFLOW.md`.

## النطاق الحالي المثبت من الكود

- Next.js 16 / React 19، مع OpenNext للنشر على Cloudflare Workers.
- MongoDB عبر `lib/mongodb.ts` وMongoose 9. يوجد MongoDB driver مباشر ضمن dependencies.
- `wrangler.jsonc` لا يحتوي على ربط D1. أكد صاحب المشروع أن القاعدة الجديدة ستُنشأ لاحقًا.
- توجد 89 ملفات API routes، و103 ملفات TypeScript في `app` و`lib` تشير إلى Mongoose أو وحدة الاتصال وقت المراجعة. هذا حصر نصي للاعتماديات، وليس عدد endpoints أو العمليات الفعلية.
- المستندات الثنائية تُخزن عبر R2 مع fallback محلي في `storage/r2_local_fallback`. توجد أيضًا وحدة قديمة للتخزين في `public/uploads/documents`؛ يجب فحص السجلات الفعلية لتحديد الملفات المستخدمة.
- يوجد backup-agent مستقل يستخدم `mongodump` و`mongorestore`. نجاح نسخه بعد التحويل لن يعني أن D1 محمية.
- توجد تعديلات محلية واسعة قبل بدء المراجعة؛ يجب الحفاظ عليها والعمل انطلاقًا منها.

## حصر النماذج

الأسماء التالية أسماء models في الكود. أسماء collections الفعلية وعددها تُستخرج من قاعدة المصدر؛ لا يجوز افتراض تطابقها مع القائمة أو الاعتماد على الجمع اللغوي لأسمائها.

| المجموعة الوظيفية | النماذج | بيانات لا يجوز إغفالها |
| --- | --- | --- |
| الحسابات والصلاحيات | User, Customer, RoleConfig | passwordHash، صلاحيات الموظفين، حالات التحقق، OTP وتواريخ انتهائها، علاقات المستخدم والعميل |
| المستندات | Document, DocumentActivityLog | مفاتيح التخزين، hashes، الملفات المؤرشفة والمرفوضة، entityType/entityId، المراجعات والتحذيرات |
| الطلبات والخدمات | CustomerRequest, RequestService, ServiceConfig, PricingRule | services بالترتيب، timeline، attachments، details الديناميكية، متطلبات المستندات والحالات |
| عروض الأسعار | Quote, QuoteItem | بنود العرض، breakdown، auditTrail، الخدمات المرتبطة، العملة والحالة |
| الحسابات المالية | Invoice, InvoiceSequence, InvoiceActivityLog, Payment | الأرقام والعدادات، tokens، كل المبالغ، المدفوعات، العملات، snapshots، سجل الأحداث |
| النظام | Notification, AnalyticsEvent, SystemSetting, SystemAuditLog | readBy، الجمهور المستهدف، سجلات الإرسال، الإعدادات والتصنيفات، سجلات النسخ والاستعادة |

## اختلافات تتطلب إعادة تنفيذ واختبار

1. `populate()` يتحول إلى joins أو استعلامات مجمعة مع الحفاظ على شكل استجابات API وحقولها المختارة. العلاقات الاختيارية لا تسقط السجل الأساسي.
2. `find` و`lean` و`select` و`sort` وpagination وعمليات العد والتحديث تحتاج repositories صريحة. تغيير `connectDB()` وحده لا يجعل Mongoose يعمل على D1.
3. `aggregate` و`distinct` في analytics تتحول إلى SQL مع مطابقة تجميع الزوار والتواريخ. البحث الحالي يستخدم Mongo regex؛ SQL LIKE ليس مطابقًا تلقائيًا، خصوصًا `%` و`_` والحروف غير اللاتينية.
4. `$inc` لترقيم الفواتير يحتاج زيادة ذرية و`RETURNING` مع الاحتفاظ بمفاتيح العدادات النصية مثل `INV_2026`، والتحقق من أعلى رقم مستخدم لكل prefix/year.
5. `InvoiceSchema.pre("save")` يحسب المتبقي وحالة الفاتورة. يجب نقل السلوك إلى خدمة مالية واضحة. الاستيراد التاريخي لا يشغل هذا الحساب ولا يغير حالة قديمة تلقائيًا.
6. `passwordHash` مخفي افتراضيًا بـ`select: false`. تصدير Mongoose الافتراضي قد يفقد تسجيل الدخول؛ النقل يحتاج قراءة MongoDB الخام مع كل الحقول.
7. subdocuments قد تحتوي `_id` وtimestamps حتى لو لم تظهر في TypeScript interfaces، مثل documentCategories. لا تُحذف باعتبارها حقولًا غير معروفة.
8. `undefined`/الحقل الغائب يختلف عن `null` في MongoDB. يلزم توثيق mapping واختبار queries قبل إسقاط هذا الفرق في SQL.
9. username يستخدم unique sparse، وSystemAuditLog يستخدم index مركب unique sparse. لا تكفي ترجمة مباشرة إلى SQLite UNIQUE؛ يجب مطابقة سلوك الغياب وnull بعد فحص بيانات المصدر.
10. `readBy` للإشعارات وarrays للخدمات وتاريخ التعديلات تحتاج حفظ الترتيب ومنع التكرار حسب السلوك الحالي، مع indexes مناسبة.

## ملاحظة مالية تمنع التحويل المباشر

في مسار MongoDB داخل `app/api/admin/payments/route.ts`، إنشاء Payment ثم حفظ Invoice ثم كتابة ActivityLog عمليات منفصلة. كما أن المسار لا يطابق صراحةً عميل الفاتورة مع العميل المرسل ولا عملة الدفع مع عملة الفاتورة. توجد مخاطرة فقد تحديث عند الدفعات المتزامنة. مسار D1 التجريبي الجديد يعالج ذلك بمعاملة واحدة وrevision ومفتاح إعادة طلب فريد؛ لا يغير التنفيذ الحالي على MongoDB.

على D1 يلزم تصميم عملية ذرية تشمل التحقق والتسجيل والتحديث والسجل، مع idempotency لمنع إعادة تسجيل نفس الطلب. `batch()` يضمن rollback عند فشل statement؛ تحديث يصيب صفر صفوف ليس خطأ SQL تلقائيًا. يجب أن يؤدي فشل الشروط إلى إلغاء كل العملية، مع اختبار متزامن حقيقي. لا نعدل الأرصدة التاريخية لمعالجة أي اختلاف قديم؛ نسجله ونراجعه منفصلًا.

## عقد حفظ البيانات

- الاحتفاظ بكل `_id` والـreferences كما هي كنص، دون إنشاء UUID بديل. ليس كل `_id` ObjectId؛ InvoiceSequence يستخدم نصًا.
- الاحتفاظ بوقت UTC ودقة milliseconds. يبقى تنسيق API كما هو، وتُختبر حدود تواريخ كشوف الحساب في منطقة التشغيل الحالية.
- حفظ نسخة خام BSON قابلة للاستعادة ونسخة canonical Extended JSON للمقارنة، شاملة الحقول غير المعرفة في النماذج وأي collections إضافية.
- تصميم جداول للأعمدة التي يتم البحث أو الربط عليها، مع JSON صالح للبيانات الديناميكية والـsnapshots. يُعتمد المخطط النهائي بعد فحص أنواع وأحجام المصدر.
- لا تغيير للدقة المالية أثناء النقل. نثبت القيم الأصلية ونفحص دقة التحويل؛ أي تحويل لوحدات نقدية صحيحة أو decimal text يجب أن يكون lossless ومختبرًا لكل عملة، وبشكل مستقل عن تصحيح الحسابات.
- لا إسقاط للتكرارات أو الروابط المفقودة لتجاوز قيود SQL. تُصدر قائمة أخطاء تمنع اعتماد النقل حتى تُحل أو تُوثق معالجة تحفظ الأصل.
- تبقى ملفات R2 خارج D1. نتحقق من وجود كل storageKey وحجم الملف وhash عند توفره، ونحصر ملفات fallback المحلي قبل النشر.

## التنفيذ على مراحل

### 1. قياس المصدر وإثبات إمكانية الاستعادة

- استخدام صلاحية قراءة فقط لحصر جميع collections والأحجام والأنواع والـindexes، وأقصى حجم سجل، مع إحصاء العلاقات المفقودة والتكرارات.
- عمل backup BSON واختبار استعادته إلى MongoDB منفصلة. checksum للأرشيف وحده لا يثبت صلاحية الاستعادة.
- حفظ manifest للأعداد وhash لكل سجل على canonical Extended JSON، مع عدم نشر بيانات أو hashes حساسة في Git أو logs عامة.
- فحص الفواتير والمدفوعات والعدادات وكشوف كل عميل لكل عملة. عدم خلط العملات في الإجماليات.
- قياس البيانات الفعلية ومقارنتها بحدود D1 للخطة المستهدفة؛ حجم MongoDB على القرص ليس تقديرًا دقيقًا لحجم SQLite بعد الفهارس.

### 2. طبقة D1 محلية واختبارات السلوك

- إنشاء migrations وbinding باسم `DB`، مع فصل قواعد local/staging/production. لا database ID افتراضي للإنتاج.
- إنشاء repositories typed بدل محاكاة Mongoose ببديل عام ناقص.
- تحويل الحسابات والصلاحيات، ثم العملاء والإعدادات، ثم المستندات، ثم الطلبات والخدمات، ثم العروض، ثم المالية والإشعارات والتحليلات.
- نقل validation/defaults/hooks صراحةً؛ لا تحديث timestamps أثناء استيراد السجلات القديمة.
- تنفيذ اختبارات دخول وصلاحيات وعزل العملاء، وحالات المستندات، وقبول/رفض العروض، والفواتير والدفعات وكشوف الحساب، والترقيم المتزامن وتكرار الطلب.
- اختبار API responses قبل/بعد ببيانات fixture معروفة، ثم بيانات staging محمية. تعطيل إرسال البريد والواتساب الحقيقي في التجارب.

### 3. أداة النقل والتحقق

- استيراد إلى قاعدة فارغة مخصصة للتجربة مع manifest ومراحل قابلة للاستئناف دون إسقاط أو overwrite صامت لبيانات مختلفة.
- حفظ حالة الفشل والخطأ لكل سجل، وفشل العملية عند وجود أي سجل غير منقول؛ لا تجاهل للأخطاء.
- استخدام SQL متوافق مع طريقة D1 للاستيراد وتقسيم الملفات وفق الحدود الحالية. لا افتراض دعم ملفات MongoDB/BSON مباشرة.
- مقارنة كل سجل بالمصدر بعد التحويل العكسي وفق mapping معتمد، وليس الاكتفاء بأعداد الصفوف أو مجموع مالي واحد.
- تشغيل quick_check وforeign_key_check المدعومين في D1 وفحص الـunique constraints، ثم المطابقة المالية واختبار الملفات. يمكن تشغيل integrity_check على نسخة SQLite مُصدّرة بأداة محلية مناسبة.

### 4. النسخ الاحتياطي والتشغيل

- إضافة نسخ D1 واستعادة مجربة إلى قاعدة منفصلة، مع توضيح نوع المحرك في واجهة الإدارة وعدم عرض Mongo backup كحماية لـD1.
- الاحتفاظ بأرشيفات MongoDB القديمة وقابلية استعادتها. مراجعة مراقبة النسخ والجداول الزمنية وسجل التدقيق.
- استبدال URI والأسرار الموجودة في إعدادات Wrangler بآلية secrets المناسبة ضمن تغيير مستقل قابل للمراجعة. لا تضمين أي قيمة سرية في التقرير.

### 5. النقل النهائي

- إنشاء D1 البعيدة بعد نجاح التجربة المحلية؛ نقل تجريبي بعيد واختبار الأداء والقيود قبل الإنتاج.
- الاتفاق على نافذة تمنع كل الكتابات، بما فيها cron والـseed وأدوات الإدارة وأي مصدر خارجي، ثم انتظار العمليات الجارية. لم يُعتمد موعد أو توقف حتى الآن.
- snapshot نهائي أثناء التجميد، ثم النقل والمطابقة الشاملة، ثم نشر الإصدار المتوافق مع binding الصحيح.
- smoke tests للقراءة والدخول والمستندات والمالية قبل فتح الكتابة. إبقاء MongoDB ونسختها الاحتياطية دون حذف.
- قبل فتح الكتابة يمكن الرجوع إلى الإصدار السابق وMongoDB المجمدة. بعد استقبال كتابات في D1، الرجوع بمجرد تغيير الاتصال يفقد تلك الكتابات؛ يلزم تجميد جديد وتصدير delta موثق ومجرب أو إصلاح النظام للأمام.

## شروط إعلان الاكتمال

- جميع collections والحقول والسجلات محسوبة، ولا توجد سجلات فاشلة أو محذوفة ضمنيًا.
- مطابقة IDs والعلاقات والتواريخ والملفات والحقول السرية، مع حفظ عدم كشفها في responses.
- مطابقة مالية لكل عميل وعملة وفاتورة ودفعة وعداد، وعدم إعادة حساب التاريخ أثناء النقل.
- اختبارات API والصلاحيات والتزامن والـcron وبناء Cloudflare ناجحة.
- استعادة D1 مجربة وrollback قبل/بعد فتح الكتابة موثق ومختبر.
- تقرير تحقق فعلي من المصدر والهدف. مراجعة الكود وحدها لا تثبت عدم فقد البيانات.

## ما لم يتم بعد

تم تصدير نسخة BSON تجريبية من MongoDB بعمليات قراءة فقط: 2072 سجلًا من 18 collection. نُقلت النسخة إلى D1 staging على الحساب الجديد، وطابقت كل السجلات المصدر، ونجحت فحوص السلامة والعلاقات. أُخذ تصدير D1 احتياطي وجُربت استعادته محليًا مع مطابقة السجلات. لم تُعتمد نافذة التجميد أو التحويل النهائي. تم إنشاء مخطط الجداول الـ19، واتصال D1، وطبقات الحسابات والعمليات والعدادات، وتصدير BSON خام مع checksums، وتجربة نقل إلى محاكي D1 مع مقارنة كل سجل. رُبطت 76 ملفات API routes بمسار D1 اختياري مع اختبارات للهوية والتزامن وعزل العملاء والمستندات والعروض والرفع وحالات فشل التخزين. ما تبقى من النظام محجوب عن MongoDB عند اختيار المعمل، وتفعيل D1 للإنتاج محظور إلى اكتمال التحويل. التحقق يشمل fixtures ونسخة حقيقية للتجربة على staging، وليس شهادة إتمام النقل النهائي. أضيف تسجيل المدفوعات ذريًا مع منع تكرار الطلب ومطابقة العميل والعملة والرصيد وسجل الدفعات؛ أضيفت قوائم الفواتير وإنشاء وتعديل وأرشفة المسودات وتأكيدها ومعاينة الأرقام مع حفظ السجل والصلاحيات والعلاقات. أضيف الإلغاء المحمي من وجود دفعات وقراءة العميل والرابط العام وكشوف الحساب لكل عملة وPDF محلي للفواتير والكشوف. أضيف طابور إرسال محلي pending وفحص انتهاء ذري وتنبيهات داخل التطبيق، وعزل وكيل نسخ Mongo عن D1. أضيف نسخ D1 محلي يشمل 23 جدولًا وتجربة استعادة في قاعدة معزولة مع مقارنة السجلات والـrevisions، وعامل إرسال افتراضي بمعاينة محلية وحماية الحالات غير المؤكدة. أضيفت تحليلات الموقع والحسابات وملخص النظام بتجميع SQL وصلاحيات حية ومنع تكرار ذري وإخفاء رموز المشاركة، وتعطيل seed في D1. نجح 142 اختبار D1 وبناء Next.js وTypeScript محليًا؛ توجد أوامر فحص بناء معزولة بقيم وهمية ومن دون نشر. توصيل مزود الإرسال الفعلي ونسخ/استعادة D1 البعيدة والملفات والتوافق النهائي مع Workers وباقي النظام ما زالت قيد التحويل. إعداد Cloudflare القديم يحتوي أسرارًا صريحة تحتاج تدويرًا قبل النشر؛ لم تستخدم للاتصال بالمصدر.

## تقدم توافق الملفات وPDF

أضيف تخزين R2 اختياري عبر bindings تجريبية، مع write-if-absent ذري، وفحص SHA256 والحجم، وnamespace مستقل للملفات الجديدة، وقراءة فقط لملفات المصدر. اختبر بقاء الملف بعد إعادة تشغيل workerd المحلي، وعدم استبدال ملف فائز في سباق رفع، وعدم حذف بايتات المصدر أثناء التنظيف. أُنشئت bucket بعيدة منفصلة باسم nilelink-d1-staging-files؛ نتائج النقل الفعلية موثقة في دليل المعمل.

أضيف تحميل خطوط PDF والشعار من ASSETS بدل الاعتماد على قرص Worker. شُغّل مولدا الفاتورة وكشف الحساب الفعليان في workerd محليًا ببيانات اصطناعية، وتمت معاينة الناتج بصريًا. هذا فحص مولدات معزولة، وليس اختبار توجيه Next كاملًا؛ ما زال اختبار staging البعيد وتجربة نسخة المصدر والمطابقة والنسخ المستقل للملفات مطلوبًا. غياب الخطوط يوقف العملية بدل fallback يفقد العربية. وضع القرص المحلي ما زال الافتراضي، واختيار وضع R2 لا يرحّل ملفات المعمل القديمة تلقائيًا.

## تحديث staging البعيدة

اختُبر تطبيق Next المبني كاملًا في معمل اصطناعي منفصل على الحساب المستهدف. عولج خلل تتبع اعتماديات البناء المعزول الذي عطّل middleware. نجحت 11 مجموعة فحوص HTTP عند تشغيل workerd محليًا مع D1/R2 البعيدتين. في التنفيذ الفعلي على Cloudflare نجحت تسع مجموعات حتى الدفعات، ونجح PDF الفاتورة، لكن كشف الحساب تجاوز حد CPU. حاول إعداد staging بحد CPU=1000ms واجتاز dry-run، ثم رفضته Cloudflare بالخطأ 100328 لأن الحساب Workers Free. لم يُغيّر الاشتراك، ولم تنشر نسخة Next الدائمة. بقيت مسودة Worker اصطناعية لتخزين مفتاحي staging؛ لا بيانات مصدر فيها. يلزم قرار المستخدم بشأن Workers Paid أو طريقة تشغيل مختلفة، ثم إكمال الفحوص؛ لا يحول الموقع قبل ذلك. نسخة النقل الأصلية أُعيد فحصها بعد الاختبارات وظلت متطابقة بجميع سجلاتها الـ2072.

تم إنشاء قاعدة nilelink-d1-staging على حساب Cloudflare الآخر بعد تسجيل المستخدم الدخول إليه، وعزل إعدادها عن Wrangler الأصلي. نجحت migrations الخمسة والمطابقة النصية لكل DDL جدول وفهرس (23 جدولًا، 65 كائن مخطط). ثم استُوردت السجلات الـ2072 وطابق كل سجل المصدر، ونجحت quick_check وforeign_key_check. حُفظ تصدير SQL بعيد وجُربت استعادته في SQLite معزولة مع مطابقة جميع السجلات. لم يتغير اتصال MongoDB أو ينشر Worker؛ اختبار التطبيق البعيد والتحويل النهائي ما زالا مطلوبين. التقرير التفصيلي محفوظ في مجلد targets الخاص المبيّن في دليل المعمل. رفض UNION أثناء فحص المخطط عولج باستعلامات SELECT منفصلة.
