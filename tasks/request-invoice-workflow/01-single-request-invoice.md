# 01 — فاتورة حالية واحدة للطلب واستبدال ذري

الحالة: مكتملة ومنشورة. يعتمد على: 00. التالي: 04، 05، 06، 07.

## السلوك المطلوب

عند ربط B بالطلب المرتبط بـA، تنفصل A عن هذا الطلب وترتبط B به في معاملة واحدة. لا يُحذف أي مستند أو دفع أو سجل. يظل شرط فاتورة أساسية واحدة لكل شحنة قائمًا بصورة مستقلة.

## قائمة التنفيذ

- [x] اعتماد مصدر واحد للعلاقة الحالية، مع قيد قاعدة بيانات يمنع فاتورتين حاليتين للطلب نفسه، لا تحقق واجهة فقط.
- [x] توحيد الاستبدال في اختيار فاتورة موجودة وفي إنشاء/فتح فاتورة من الطلب، بما في ذلك حالة وجود فاتورة للشحنة مسبقًا.
- [x] التحقق من ملكية العميل وصلاحية التعديل وحالة الفاتورة، ومنع نقل فاتورة من طلب آخر بصمت.
- [x] فصل A وربط B وتحديث السجل في معاملة ذرية تتحقق من مراجعات الطلب والفواتير؛ طلبان متزامنان لا يتركان رابطين أو يفقدان العلاقة.
- [x] إعادة اختيار B نفسها عملية بلا تكرار في السجل أو الإشعارات.
- [x] سجل التدقيق يحدد الطلب والسابقة والجديدة والموظف والوقت وسبب الاستبدال إن كان مطلوبًا بالواجهة.
- [x] معالجة العلاقات التاريخية المتعددة بمراجعة واضحة قبل إضافة القيد؛ الاحتفاظ بكل الفواتير والمدفوعات والنسخ المنشورة.
- [x] توحيد استجابة APIs والبطاقات على فاتورة حالية واحدة، وإزالة الافتراض السابق بالسماح بمتعدد.
- [x] إرجاع نتيجة الربط اللازمة لمهمة الإشعارات دون إعادة جلب بيانات مالية حساسة للعميل.

## أثر استبدال فاتورة منشورة بمسودة

الطلب لا يعرض للعميل المسودة الجديدة. الفاتورة القديمة تُفصل عن الطلب، لكنها تبقى مستندًا ماليًا منشورًا في سجل العميل إن كانت صالحة، ولا تُلغى أو تُحذف لمجرد الاستبدال. لا يُعاد استخدام مبلغها كأنه قيمة المسودة الجديدة.

## اختبارات ومعايير القبول

- [x] ربط A ثم B ينتج رابطًا حاليًا واحدًا فقط؛ A باقية بأرقامها ومدفوعاتها ونسخها.
- [x] إنشاء فاتورة من الطلب يستبدل القديمة بنفس القواعد، ولا يكرر فاتورة الشحنة.
- [x] فشل السجل أو تحديث أي طرف يعيد المعاملة كاملة، دون طلب بلا رابط نتيجة فشل جزئي.
- [x] إعادة المحاولة والتزامن ينتجان نتيجة واحدة متسقة؛ إعادة نفس الربط لا تكرر الأحداث.
- [x] عميل مختلف/موظف دون صلاحية/فاتورة مرتبطة بطلب آخر يُرفضون من الخادم.
- [x] لا تتسرب المسودة الجديدة عبر تفاصيل الطلب أو عدّاد العميل أو رابط/PDF الفاتورة.
- [x] اختبار الترحيل على نسخة معزولة بها علاقات متعددة، مع إثبات حفظ عدد المستندات والمدفوعات.

## نقطة الاستئناف الحالية

الحالة: جارٍ التنفيذ والاختبار محليًا. أضيف مساعد مشترك `lib/shipments/request-invoice-link.ts` يجهز فصل الفاتورة السابقة وتحديث الطلب وسجل الربط في نفس المعاملة. يستخدمه الربط المباشر وإنشاء حسابات الشحنات والإنشاء/التعديل في نظام الفواتير العام. تحديث مراجعة الطلب يمنع عمليتين متزامنتين من النجاح معًا. أضيف migration `0010_request_invoice.sql` لقيد فريد على relatedRequestId وتوافق النسخ الاحتياطية مع القيد القديم والجديد.

نجح 51 اختبارًا للحسابات والفواتير؛ يجري التحقق الإضافي من الإنشاء الذي يستبدل فاتورة قائمة ومن النسخ الاحتياطية. لا يزال يلزم: اكتمال البناء، اختبار HTTP على التجربة بالقيد الجديد، تحديث عامل النسخ الاحتياطية، نشر التطبيق، تطبيق آخر تعيين مثبت بسجل التدقيق للتعارض الموجود، ثم إضافة القيد على الإنتاج وفحص البيانات. لا تعتبر المهمة منشورة قبل تسجيل هذه الأدلة.
