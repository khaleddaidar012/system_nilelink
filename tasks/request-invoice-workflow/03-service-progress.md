# 03 — حالة كل خدمة والمراحل التشغيلية للطلب

الحالة: لم تبدأ. يعتمد على: 00 و02. التالي: 05.

## المطلوب

الأدمن والموظف المسؤول المصرح له يحدّثان تقدم الخدمة من الطلب/الشحنة، والعميل يرى المرحلة الحالية وحالة كل خدمة مطلوبة وتاريخ التحديث.

## ضوابط النطاق

- المصدر هو الخدمات المختارة فعلًا: شحن، نقل، تخليص، أو غيرها الموجودة. لا تُعرض خدمة غير مطلوبة كعائق، ولا يُفرض تنفيذ المراحل الثلاث على كل طلب.
- ورد الشحن مرتين في الوصف. ثبّت هل المقصود حجز الشحن ثم الإبحار/التسليم قبل إنشاء مرحلتين مستقلتين؛ حتى ذلك الحين لا تضف تكرارًا إجباريًا.
- اكتمال مرحلة مالية في الفاتورة ليس تحديثًا تلقائيًا للحالة التشغيلية، والعكس. النشر لا يحدث عند تغيير حالة الخدمة.

## قائمة التنفيذ

- [ ] تعريف حالات خدمة معتمدة وانتقالات واضحة، مثل لم تبدأ/جارية/مكتملة/متوقفة، مع ربطها بالقيم الموجودة دون كسر السجلات.
- [ ] منع قيم الحالة العشوائية في `service-status` والتحقق من ارتباط الخدمة بالطلب والموظف المسؤول وصلاحياته.
- [ ] تسجيل التاريخ والفاعل والتعليق الاختياري في timeline، والتحكم في التعليق المرئي للعميل مقابل الداخلي.
- [ ] تحديث ملخص الطلب والمرحلة الحالية من الخدمات المطلوبة دون فقد حالة الخدمات المتوازية.
- [ ] إتاحة الرجوع/التصحيح المصرح به مع سجل، ومنع القفزات غير الصالحة التي يعتمد عليها تنفيذ آخر.
- [ ] إضافة أدوات التحديث في تفاصيل الطلب والشحنة حيث العلاقة موجودة، وعدم إنشاء رابط شحنة تخميني.
- [ ] إظهار UCR/ACID وحالته دون خلطه برقم الفاتورة أو الحالة المالية.
- [ ] توحيد API المصدر الذي يستخدمه الموظف والعميل مع إسقاط الحقول الداخلية.

## ملفات البداية

- `lib/workflows/requests.ts`، `app/api/admin/services/[id]/status/route.ts`.
- Models وجداول `customer_requests` و`request_services` و`shipment_records` الحالية.
- `app/[locale]/admin/requests/[id]/page.tsx`، مكونات الشحنات، وصفحة طلب العميل.

## اختبارات ومعايير القبول

- [ ] طلب نقل فقط يعرض النقل والفاتورة دون انتظار الشحن والتخليص.
- [ ] طلب متعدد الخدمات يعرض حالة كل خدمة والمرحلة الحالية بوضوح، مع دعم الخدمات المتوازية إن وجدت.
- [ ] موظف غير مسؤول/غير مخول لا يحدث خدمة عبر تخمين المعرّف.
- [ ] تحديث المرحلة لا ينشر مسودة ولا يغير تكلفة أو مبلغًا ماليًا.
- [ ] حالات قديمة غير مطابقة تُعالج بترحيل/عرض متوافق موثق، دون محو تاريخها.
- [ ] التحديث المتزامن لا يفقد timeline أو أحدث حالة محفوظة.
