# 06 — إشعار العميل بتعيين الفاتورة ونشرها

الحالة: لم تبدأ. يعتمد على: 01 و04. التالي: 07 و09.

## السلوك المعتمد

| الحدث | إشعار العميل |
|---|---|
| تعيين فاتورة منشورة للطلب | إشعار فوري بتعيين الفاتورة ورابط الطلب/المعاينة |
| تعيين فاتورة Draft | لا إشعار بالفاتورة ولا كشف بياناتها؛ يُنتظر النشر |
| نشر الفاتورة الحالية المعيّنة | إشعار واحد بالنشر والتعيين دون تكرار لنفس الحدث |
| إعادة اختيار نفس الفاتورة | لا إشعار جديد |
| حفظ تكاليف/ملاحظات داخلية أو مراجعة Draft | لا إشعار للعميل ولا كشف للتغييرات |
| نشر مراجعة للفاتورة الحالية | إشعار واضح بتحديث النسخة المنشورة |
| استبدال فاتورة بمنشورة أخرى | إشعار واحد بتعيين الجديدة، دون إلغاء مالية القديمة |

المطلوب إشعار داخل النظام. لا إرسال بريد أو واتساب أو رسالة خارجية تلقائيًا ضمن هذه المهمة.

## قائمة التنفيذ

- [ ] مراجعة إشعار النشر الحالي في `shipment-invoices` وإعادة استخدام خدمة الإشعارات الحالية.
- [ ] إنشاء حدث التعيين ضمن معاملة الربط أو آلية موثوقة مكافئة؛ لا إشعار بمعاملة فشلت.
- [ ] عند نشر مسودة كانت معيّنة، إصدار إشعارها في النشر دون ربط جديد يدويًا.
- [ ] توحيد النشر والتعيين بمفتاح عدم تكرار حسب الطلب والفاتورة والنسخة/عملية التعيين، مع عدم منع إشعار تعيين جديد مشروع لاحقًا.
- [ ] التحقق من أن الفاتورة ما زالت الحالية وقت الحدث؛ سباق الاستبدال والنشر لا يرسل رابطًا قديمًا باعتباره الحالي.
- [ ] النص العربي/الإنجليزي يتضمن رقم الفاتورة ورقم الطلب والحالة ورابطًا مصرحًا به، دون تكاليف أو ربح أو بيانات داخلية.
- [ ] ظهور الإشعار والعداد في بوابة العميل، وتسجيل القراءة لكل مستخدم حسب آلية النظام الحالية.
- [ ] الروابط القديمة لا تمنح صلاحية أو تكشف مسودة إذا تغيرت العلاقة لاحقًا.

## اختبارات ومعايير القبول

- [ ] كل صف في جدول السلوك له اختبار، بما فيه انعدام إشعار العميل للمسودات.
- [ ] فشل الحفظ/الربط/النشر لا يترك إشعار نجاح يتيمًا.
- [ ] التزامن وإعادة المحاولة لا يكرران نفس الإشعار.
- [ ] لا وصول لمستخدم من عميل آخر، ولا كشف مبالغ غير منشورة في عنوان أو رسالة أو payload الإشعار.
- [ ] لا يرسل تبديل الصفحات أو polling إشعارات إضافية.
