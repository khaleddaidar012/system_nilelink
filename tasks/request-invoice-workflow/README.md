# خطة استكمال الطلبات والخدمات والفواتير

تاريخ المتطلبات: 8 نوفمبر 2026 — الحالة: الفحص ومهمة 01 مكتملان ومنشوران، ومهمة 02 قيد التنفيذ.

## نطاق هذه الدفعة

المطلوب حاليًا توثيق العمل في ملفات مستقلة قابلة للاستئناف. إنشاء هذه الملفات لا يعني تنفيذ المتطلبات الجديدة أو نشرها. لا تغيّر بيانات الإنتاج عند قراءة هذه الخطة.

## المتطلبات المعتمدة

1. لكل طلب فاتورة مرتبطة حالية واحدة كحد أقصى. اختيار أخرى يفصل السابقة عن الطلب، ولا يحذف الفاتورة أو مدفوعاتها أو نسخها المنشورة.
2. العميل يتلقى إشعارًا بتعيين فاتورة منشورة له. إذا عُينت مسودة، يتأجل إشعار العميل حتى نشرها. المسودة لا تظهر له في أي API أو صفحة أو عدّاد.
3. عرض السعر اختيار يحدده الموظف في الطلب، لا شرط دائمًا لتنفيذ الخدمة. المسار المباشر للعميل الحالي يدعم UCR أو ACID المناسب، ثم تنفيذ الخدمات وإصدار الفاتورة دون فرض عرض سعر.
4. الموظف المصرح له أو الأدمن يحدّث حالة الخدمات المطلوبة، والعميل يرى موقع طلبه وتاريخه التشغيلي.
5. يمكن متابعة الفاتورة وإعدادها من داخل الشحنة والطلب، مع بقاء النشر مستقلًا وصلاحيات الربح للأدمن فقط.
6. يظهر عدّاد تحديثات الحسابات في القائمة الجانبية للأدمن والموظفين المصرح لهم؛ القراءة تخص كل مستخدم، والجديد يعود بعد القراءة.
7. تظهر حالة كل خدمة وزر «معاينة الفاتورة» عند العميل بعد النشر فقط.
8. تعالج عيوب عرض الفاتورة الظاهرة بالصور: مفتاح ترجمة الحالة الخام، ورمز الدولار المخالف لعملة EGP.

## الوضع الموجود قبل بدء الحزمة

- المشروع Next.js / React / next-intl / Cloudflare D1 وR2، وله نظام حسابات قائم. يُستخدم كما هو دون إنشاء نظام موازٍ.
- الفواتير مرتبطة بالشحنة بواسطة `shipmentRecordId` وبالطلب بواسطة `relatedRequestId`.
- يوجد قيد فريد لفاتورة الشحنة الأساسية؛ **لا يوجد بعد ضمان لفاتورة واحدة لكل طلب**. الصورة المرفقة تظهر فاتورتين للطلب نفسه.
- زر «ربط / إنشاء فاتورة» موجود، ويوفر الاختيار أو الإنشاء من الحسابات، لكن الاستبدال التلقائي ليس منفذًا بعد.
- المسودات مخفية عن العميل، والنسخ المنشورة محفوظة. النشر متاح عند اكتمال أي مرحلة واحدة مع سعر بيع موجب ومعاينة محفوظة؛ لا يُعاد اشتراط المراحل الثلاث.
- توجد إشعارات عند النشر، لكن إشعار تعيين فاتورة موجودة والتكرار مع النشر يحتاجان المراجعة والتنفيذ.
- توجد حالات وتواريخ لخدمات الطلب، لكن المسار التشغيلي والواجهة المطلوبة يحتاجان استكمالًا.
- واجهة عدّادات العمل الحالية تحتوي قسم `invoices`، بينما رابط الحسابات `/admin/shipment-invoices` يحتاج ربطه بالأحداث والقراءة والصلاحيات.
- آخر نسخة منشورة تم التحقق منها في الجلسة السابقة: `db02c307-f942-4563-9062-5e2e9590b684`. أعد التحقق عند الاستئناف؛ ليست ضمانًا بأن الإنتاج لم يتغير بعدها.
- نجح 50 اختبارًا محليًا و13 مجموعة تحقق على بيئة التجربة قبل هذه الحزمة. لا تُحسب هذه النتائج دليلًا على تنفيذ المتطلبات الجديدة.
- مرجع التنفيذ السابق: `docs/shipment-accounting-implementation.md`.

## ضوابط مشتركة

- احترام الحسابات والعملاء والأدوار والصلاحيات الحالية؛ الوصول المباشر للـAPI يخضع لنفس القيود.
- Draft داخلية. العميل يرى آخر نسخة منشورة مصرحًا له بها فقط، دون التكاليف أو الربح أو ملاحظات الموظفين.
- الربح للأدمن فقط. سعر البيع هو قيمة الفاتورة، والربح = سعر البيع − التكاليف، والحسابات المالية الدقيقة الموجودة تُحفظ.
- فصل الحالة التشغيلية للخدمة عن خانة اكتمال المرحلة المالية؛ تحديث الحالة لا ينشر الفاتورة تلقائيًا.
- الحفاظ على عدم قابلية تعديل النسخة المنشورة بصمت، وسجل التدقيق، والتحقق على الخادم، ودعم العربية والإنجليزية وRTL/LTR.
- استخدام نمط المعاملات والقفل التفاؤلي الحالي. لا تسمح إعادة المحاولة بتكرار الربط أو الإشعارات.
- لا تحذف فواتير أو مدفوعات أو سجلات، ولا تنشر فواتير حقيقية أثناء الاختبار، ولا تعيد حساب مستند منشور كأثر جانبي.
- لا تنفيذ لترحيل بيانات متعارضة باختيار عشوائي. اعرض الحالات والقرار المطلوب أولًا.

## الاستئناف بعد نفاد الكوتا أو تغيير الجلسة

1. اقرأ هذا الملف ثم سجل الاستئناف في آخر مهمة جارٍ العمل عليها.
2. افحص `git status` والملفات الفعلية وAGENTS.md إن وُجد. توجد تعديلات كثيرة سابقة؛ لا تتراجع عنها ولا تعيد إنشاء المنجز.
3. تحقق من مصدر قاعدة البيانات والبيئة قبل أي كتابة. ملفات `.private` قد تحتوي أسرارًا؛ لا تطبعها أو تنقلها إلى ملفات التاسكات.
4. أكمل المهمة الجارية واختباراتها، وحدّث حالة الجدول وسجلها قبل الانتقال للتالية.
5. لا تكتب «مكتملة» إلا بعد استيفاء معايير القبول وتسجيل دليل الاختبار. ميّز بين منفذة محليًا ومختبرة على التجربة ومنشورة.
6. عند التوقف سجل آخر نتيجة، الأخطاء، الاختبارات الباقية، والعملية التالية بالضبط. أرقام جلسات الأدوات لا يُعتمد عليها بعد إعادة تشغيل التطبيق.

## نقاط تحتاج تثبيتًا قبل التنفيذ المعني

- «عميل جديد» لا يُستنتج من الاسم أو وجود الحساب فقط. استخدم اختيارًا صريحًا للمسار في الطلب؛ لا تتجاوز عرض سعر سابقًا دون قرار محفوظ.
- ورد «الشحن ثم النقل ثم التخليص ثم الشحن ثم الفاتورة». الخدمات المطلوبة هي مصدر المراحل. إذا لزم التفريق بين حجز الشحن والإبحار/التسليم فثبّت المعنى قبل إضافة مرحلة شحن ثانية.
- عند وجود فاتورتين حاليًا للطلب، تحديد الفاتورة الحالية المطلوب إبقاؤها جزء من معالجة البيانات، مع إبقاء الباقي في السجل المالي.
